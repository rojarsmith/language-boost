# 計畫式升級：每一階段先能用，再驗收

使用者於 2026-10-13 決定先做可放在 Vercel 的小型 POC，後續按計畫升級。每日目標 90 分鐘以上，先以產品／專案／技術業務為主。以下時間是驗證建議，不是流利或錄取保證；未排程任何自動任務。

| 階段 | 範圍 | 進入下一階段的條件 | 狀態 |
| --- | --- | --- | --- |
| 0.1 · Vercel POC | 靜態前端、英日情境、播放與回聽、本機習慣紀錄、匯出、間隔重用 | 使用者完成 7 天試練，確認主要卡點與可持續流程；實機音訊可用 | 本版已實作，尚未雲端部署 |
| 0.2 · 多使用者 MVP | Ubuntu API、正式登入、資料隔離、跨裝置同步、資料匯入、備份與還原 | 兩個帳號的隔離與跨裝置同步通過測試；備份還原可驗證 | 待 POC 驗證後規劃與實作 |
| 0.3 · 針對卡點升級 | 優先選一項：真人音訊、可變追問、文字回饋或更好的遷移測驗 | 能改善實際陌生情境表現，成本、延遲與隱私可接受 | 尚未實作 |

## 第一階段先回答什麼

1. 能否每天完成至少一個六步情境，而不是只讀範本？
2. 看得懂但聽不懂，還是聽懂但說不出？使用者每次標記最卡的環節。
3. 關閉提示後，能否用自己的內容說明需求、產品價值與取捨？
4. 換問法或多一個追問時，能否回應或主動澄清？
5. 真人錄音或真人問法的效果，是否也有所改善？POC 不自動判定答案品質。

## 七天試練建議

| 日 | 優先任務 | 留下什麼 |
| --- | --- | --- |
| 1 | 澄清句、自介 | 初次錄音與三項最卡問題 |
| 2 | 自介重用、需求訪談 | 用真實工作替換範例 |
| 3 | 產品價值、生活點餐 | 不靠技術名詞堆砌的三句說明 |
| 4 | 時程與取捨、到期複習 | 明確的選項、期限與下一步 |
| 5 | 客戶異議、困難經驗 | 接住顧慮與具體行動 |
| 6 | 混合情境、關閉部分提示 | 新問法與陌生情境的回答 |
| 7 | 真人陪練／真人音訊，加上匯出 | 與第一天比較：是否答到問題、是否可澄清、是否可回應追問 |

每天 90 分鐘可分為理解訊息 20、表達 25、語言細節 20、流暢度／重用 25 分鐘。不需一天新增所有任務；已有瓶頸時縮短句子、降低速度、重做同一任務。英語先作主線；日語可換日練，不要求同一天完成兩套 90 分鐘。

## 第二階段的部署方向（尚未實作）

保留靜態前端與教材資料契約，用 API 替換本機儲存層。可選 Vercel 前端透過 `/api` 反向代理 Ubuntu API，或由 Ubuntu 反向代理同時提供前端與 API。部署選項參考 [Vercel 外部 rewrites](https://vercel.com/docs/routing/rewrites)。

資料至少拆成 users、preferences、attempts、review_schedule。每筆練習使用固定 ID，匯入與重試不能重複計數；查詢按經驗證的使用者 ID 隔離。先採小型 VPS 可維護的資料庫，不在 POC 階段加入分散式服務。

正式帳號階段才處理密碼／身分服務、忘記密碼、同步衝突、保留期限、刪除、API 配額與備份。POC 匯出應保留教材版本、lesson_id、語言、時間、回答與偏好，後續由明確匯入流程遷移；不能把 localStorage 當正式多使用者資料庫。

## 第三階段的選擇原則

先看試練結果：辨音最卡就先增加短段真人錄音與口音；組織答案最卡才評估可控文字回饋；追問最卡才評估可變對話。一次只加一項核心能力，重新驗收後再擴大。AI 只能根據取得的資料回饋；只有文字時不產生發音分數，不以外國人刻板印象推導文化建議。
